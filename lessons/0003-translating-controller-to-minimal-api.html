บทที่ 3 จาก 6 · Controller-based vs Minimal API

เขียน Minimal API ชุดเดียวกัน

คุณอ่าน Program.cs ออกแล้ว (บทที่ 1) และอ่าน syntax C# ในไฟล์ตัวเองได้ทุกบรรทัดแล้ว (บทที่ 2) บทนี้เราจะทำสิ่งที่คอร์สนี้รอคอย — แปลง TodoItemsController ของคุณเป็น Minimal API แบบ line-by-line แล้วดูกันให้ชัดว่า อะไร หายไป อะไร ยังอยู่เดิมทุกประการ

เป้าหมายบทนี้

เปิด Controllers/TodoItemsController.cs ค้างไว้ข้างๆ แล้วอ่านเทียบไปทีละส่วน จบบทนี้คุณจะมีโค้ด Minimal API ชุด CRUD ชุดเดียวกับของคุณ — ที่รันได้จริง — อยู่ในมือ

ผู้เล่นเดิมทั้งหมด — เปลี่ยนแค่ "เปลือก"

ก่อนลงโค้ด ให้เห็นภาพใหญ่ก่อนว่าสิ่งที่เปลี่ยนคืออะไรบ้าง ทุกอย่างในคอลัมน์กลางยังเป็นของเดิมเป๊ะ

1 · GET อันแรก — ดู side by side

ซ้ายมือคือโค้ดคุณทุกวันนี้ ขวามือคือ Minimal API ที่ทำงานเหมือนกันทุกประการ:

// ===== ฝั่ง Controller (โค้ดคุณ) =====
[HttpGet]
public async Task<ActionResult<IEnumerable<TodoItemDTO>>> GetTodoItems()
{
    var todos = await _context.TodoItems.Include(t => t.Category).ToListAsync();
    var result = todos.Select(t => new TodoItemDTO(t)).ToList();
    return Ok(result);
}
// ===== ฝั่ง Minimal API =====
group.MapGet("/", async (TodoDb db) =>
{
    var todos = await db.TodoItems.Include(t => t.Category).ToListAsync();
    var result = todos.Select(t => new TodoItemDTO(t)).ToList();
    return TypedResults.Ok(result);
});
  • บรรทัด query 3 บรรทัดแรก = คัดลอกมาเป๊ะ — เปลี่ยนแค่ _context เป็น db (ชื่อ parameter)
  • ไม่มีคลาส ไม่มี constructor ไม่มี attribute เหลือเลย — เส้นทาง + method ถูกรวมเป็น MapGet("/", ...) บรรทัดเดียว
  • TodoDb db ไม่ได้มาจากการประกาศตัวแปร — มันคือ parameter ที่ DI เติมให้เอง เพราะ AddDbContext<TodoDb>() ลงทะเบียนไว้แล้วใน Program.cs ของคุณ (บรรทัดเดิม ไม่ต้องแก้)

Aha! — constructor ถูกแทนที่ด้วย parameter

บทที่ 1 เราเห็นว่า DI ยัดของใส่ constructor ของ controller — ใน Minimal API กลไกเดียวกันนี้ ย้ายไปที่ parameter ของ route handler แทน ถ้าชนิดไหนลงทะเบียนอยู่ใน container คุณก็เขียนรับเป็น parameter ได้เลย ไม่ต้องใช้ [FromServices] ก็ได้

2 · กฎ parameter binding — request อะไร เข้า parameter ไหน

นี่คือหัวใจที่ทำให้ Minimal API สั้น — framework "เดา" ให้เองจากชนิดและ HTTP method (อ้างอิง: Parameter binding — Microsoft Learn)

Parameterถูกเติมมาจากตัวอย่างในโค้ดคุณ
int idRoute value (ส่วน {id} ใน URL)MapGet("/{id:int}", (int id, ...) => ...)
TodoItemDTO dtoBody ของ request (JSON) — POST/PUT เท่านั้นMapPost("/", (TodoItemDTO dto, ...) => ...)
TodoDb dbDI containerทุก handler ในบทนี้
int page (ที่ไม่มีใน URL)Query string — เช่น ?page=2ไม่ได้ใช้ในโปรเจกต์นี้ แต่รู้ไว้ใช้ตอนท้าย

ข้อควรจำ: HTTP method ที่ GET, HEAD, OPTIONS และ DELETE ไม่อ่าน body ให้อัตโนมัติ — ถ้าจะส่ง body ต้องระบุ [FromBody] ตรงๆ ส่วน POST/PUT อ่านให้เอง

3 · POST — จุดที่ต่างชัดที่สุด: สร้าง "ที่อยู่" ให้ของใหม่

บรรทัดสุดท้ายของ CreateTodoItem คุณใช้ CreatedAtAction ซึ่งผูกกับชื่อ action — Minimal API ไม่มีชื่อ action จึงสร้าง URL ตรงๆ: 

// ฝั่ง Controller — ผูกกลับไปหาเมธอด GetTodoItem (ชื่อ action)
return CreatedAtAction(nameof(GetTodoItem), new { id = todoItem.Id }, new TodoItemDTO(todoItem));

// ฝั่ง Minimal API — เขียน path ให้เห็นตรงๆ (หรือใช้ .WithName() + link generator ก็ได้)
return TypedResults.Created($"/api/todoitems/{todoItem.Id}", new TodoItemDTO(todoItem));

ผลลัพธ์ เหมือนกันทุกประการ: ตอบ 201 Created พร้อม header Location ชี้ไปที่ของที่เพิ่งสร้าง — เหมือนกับที่ controller ของคุณทำอยู่ตอนนี้

ส่วนเนื้อในของ handler คัดลอกจากโค้ดคุณได้ทั้งดุ้น ไม่มีอะไรต้องคิดใหม่:

group.MapPost("/", async (TodoItemDTO dto, TodoDb db) =>
{
    var categoryExists = await db.Categories.AnyAsync(c => c.Id == dto.CategoryId);
    if (!categoryExists)
        return TypedResults.BadRequest(
            new { message = $"ไม่พบหมวดหมู่ ID: {dto.CategoryId} ในระบบกรุณาตรวจสอบอีกครั้ง" });

    var todoItem = new TodoItem
    {
        Title = dto.Title,
        IsComplete = dto.IsComplete,
        DueDate = dto.DueDate ?? DateTime.UtcNow.AddDays(1),
        CategoryId = dto.CategoryId
    };

    db.TodoItems.Add(todoItem);
    await db.SaveChangesAsync();
    await db.Entry(todoItem).Reference(t => t.Category).LoadAsync();

    return TypedResults.Created($"/api/todoitems/{todoItem.Id}", new TodoItemDTO(todoItem));
});

4 · ค่าที่ return ได้ — 3 แบบ

return อะไรframework ทำอย่างไรContent-Type
stringเขียนลง response ตรงๆtext/plain
new { ... } หรือ DTOJSON-serialize ให้เองapplication/json
IResult เช่น TypedResults.Ok(x)เรียก method ของ object นั้นตามชนิดของ result

Microsoft แนะนำให้ใช้ TypedResults มากกว่า Results เพราะ compiler รู้ชนิดที่แน่นอน และช่วยให้สร้างเอกสาร OpenAPI ได้แม่นยำขึ้น — บทที่ 5 เราจะได้เห็นผลของมันจริงๆ

5 · โค้ดทั้งหมดต้องอยู่ใน Program.cs เหรอ? — ไม่จำเป็น

Minimal API ไม่ผูกกับ Program.cs — นิยมแยกเป็นไฟล์คลาส static แล้วเรียกนัดเดียว: 

// Program.cs — ครึ่งหลัง "ต่อท่อ" เหมือนเดิมทุกประการ เพิ่มแค่บรรทัดเดียว
app.UseHttpsRedirection();
TodoItemsEndpoints.MapTodoItems(app);   // <-- แทนที่ app.MapControllers();
app.Run();
// Endpoints/TodoItemsEndpoints.cs — รวมทุก endpoint ของเรื่องนี้ไว้ไฟล์เดียว
public static class TodoItemsEndpoints
{
    public static void MapTodoItems(this WebApplication app)
    {
        var group = app.MapGroup("/api/todoitems");      // เส้นทางฐาน = [Route("api/[controller]")]

        group.MapGet("/", GetTodoItems);                 // [HttpGet]
        group.MapGet("/{id:int}", GetTodoItem);          // [HttpGet("{id}")]
        group.MapPost("/", CreateTodoItem);              // [HttpPost]
        group.MapPut("/{id:int}", UpdateTodoItem);       // [HttpPut("{id}")]
        group.MapDelete("/{id:int}", DeleteTodoItem);    // [HttpDelete("{id}")]
    }

    // handler = เมธอดธรรมดาก็ได้ — ใช้ async Task<IResult> เหมือนกันทุกตัว
    private static async Task<IResult> GetTodoItems(TodoDb db) { ... }
    private static async Task<IResult> GetTodoItem(int id, TodoDb db) { ... }
    private static async Task<IResult> CreateTodoItem(TodoItemDTO dto, TodoDb db) { ... }
    private static async Task<IResult> UpdateTodoItem(int id, TodoItemDTO dto, TodoDb db) { ... }
    private static async Task<IResult> DeleteTodoItem(int id, TodoDb db) { ... }
}

สังเกตว่า Program.cs ครึ่งแรก (สั่งของ) ไม่ต้องแก้อะไรเลย — AddDbContext<TodoDb>, AddOpenApi ยังอยู่ที่เดิม เปลี่ยนเฉพาะครึ่งหลังบรรทัดเดียวเท่านั้น

ก่อนจะลอง — อย่าเพิ่งใช้เส้นทางเดียวกัน

ถ้าคุณ register endpoint ที่ /api/todoitems พร้อมกับ ที่มี controller อยู่แล้ว สอง endpoint จะแย่งเส้นทางเดียวกัน แล้ว request แรกที่เข้ามาจะโดน AmbiguousMatchException (HTTP 500) ทันที — ผมทดสอบยืนยันแล้ว ดังนั้นตอนทดลอง ให้ใช้ prefix ชั่วคราว เช่น /minimal/todoitems ก่อน แล้วค่อยสลับเมื่อพร้อมแทน controller จริงๆ

จุดที่ "ไม่เหมือน" จุดเดียวที่ต้องรู้ตอนนี้

[Required] / [StringLength] ใน TodoItemDTO ของคุณ — ตอนอยู่กับ controller มันทำงานอัตโนมัติเพราะ [ApiController] เป็นคนเปิดให้ แต่ใน Minimal API validation ไม่วิ่งเอง ถ้าไม่ลงทะเบียน builder.Services.AddValidation(); แปลว่าข้อมูลผิดๆ จะวิ่งเข้าไปถึง handler เลย (Microsoft ระบุไว้ชัดใน docs) เรื่องนี้คือ 1 ใน criteria หลักที่ใช้ตัดสินใจ — เราเจาะจริงจังในบทที่ 4

ลองของจริง (15 นาที) — รันสองสไตล์พร้อมกัน

  1. สร้างไฟล์ใหม่ Endpoints/TodoItemsEndpoints.cs แล้วคัดลอกโครงโค้ดข้อ 5 ไปวาง (เติมเนื้อ handler จากข้อ 1–3)
  2. เปลี่ยน prefix ใน MapGroup เป็น /minimal/todoitems ก่อน (กันชนกับ controller เดิม)
  3. เพิ่ม TodoItemsEndpoints.MapTodoItems(app); ใน Program.cs ก่อน app.Run() แล้ว dotnet run
  4. ยิงทั้งสองเส้นทางใน TodoApiV2.http แล้วเทียบ JSON: 
    GET http://localhost:5018/api/todoitems        # ฝั่ง controller
GET http://localhost:5018/minimal/todoitems    # ฝั่ง minimal API
    ต้องได้ผลลัพธ์ เหมือนกันเป๊ะ ทุก field
  5. เมื่อมั่นใจ ค่อยเปลี่ยน MapGroup เป็น /api/todoitems แล้วคอมเมนต์ app.MapControllers(); ออก — ตอนนี้ Minimal API รับช่วงแทน controller เต็มตัว (ลบไฟล์ controller เก็บไว้ก่อน อย่าเพิ่งทิ้ง)

1 · ใน Minimal API อะไรแทนที่ constructor ที่รับ TodoDb context?

AddDbContext<TodoDb>() ใน Program.cs ลงทะเบียน TodoDb ไว้แล้ว พอ handler รับ parameter เป็นชนิด TodoDb DI ก็ยัดใส่ให้ทันที — กลไกเดียวกับ constructor injection ในบทที่ 1 เปลี่ยนแค่ "ตำแหน่งที่รับของ" จาก constructor มาเป็น parameter

2 · TypedResults.Created(...) ต่างจาก TypedResults.Ok(...) อย่างไร?

Created = 201 Created พร้อม header Location ชี้ไปที่ของที่เพิ่งสร้าง (มาตรฐาน HTTP สำหรับ "สร้างของใหม่สำเร็จ") ส่วน Ok = 200 ธรรมดา ไม่มี Location — controller ของคุณก็ใช้ CreatedAtAction ซึ่งให้ผล 201 + Location เหมือนกัน

3 · group.MapPost("/", (TodoItemDTO dto, ...) => ...) — parameter dto ถูกเติมมาจากไหน?

POST/PUT อ่าน body (JSON) ให้อัตโนมัติสำหรับ complex type ส่วน GET/HEAD/OPTIONS/DELETE ไม่อ่าน body ให้เลย และถ้าชนิดนี้ลงทะเบียนใน DI จะถูกดึงจาก container ด้วย — ในกรณีนี้ TodoItemDTO ไม่ได้ลงทะเบียน จึงมาจากร่าง JSON ของ request

4 · ถ้า register endpoint ที่ /api/todoitems ทั้งที่ controller เดิมก็ใช้เส้นทางนี้อยู่ จะเกิดอะไร?

routing เจอสอง endpoint ที่แม่นยำเท่ากัน แล้วตัดสินไม่ได้ว่าใครควรรับ — จึงโยน AmbiguousMatchException ทันที (ผมทดสอบกับ .NET 10 แล้ว ได้ 500) วิธีปลอดภัยคือใช้ prefix คนละอันตอนทดลอง หรือปิดอันใดอันหนึ่งไปก่อน

5 · ทำไม [Required] ใน TodoItemDTO อาจ "ไม่ทำงาน" เมื่อใช้ Minimal API?

ฝั่ง controller นั้น [ApiController] เป็นคนเปิด validation ให้อัตโนมัติ แต่ฝั่ง Minimal API ต้องเรียก builder.Services.AddValidation(); ใน Program.cs — ถ้าไม่เรียก Microsoft ระบุชัดว่า "no automatic validation runs" คือข้อมูลผิดจะวิ่งเข้า handler เลย เรื่องนี้คือหนึ่งใน criteria หลักของบทที่ 4

6 · ข้อใดกล่าวถูกต้องเกี่ยวกับสิ่งที่ "ไม่เปลี่ยนเลย" ระหว่างสองสไตล์?

สองสไตล์นี้อยู่ใน ASP.NET Core ตัวเดียวกัน — Program.cs ครึ่งแรกไม่ต้องแก้เลย AddDbContext, AddOpenApi, EF Core query, TodoItemDTO, middleware pipeline ทุกอย่างเป็นของเดิม สิ่งที่เปลี่ยนมีแค่ "เปลือกที่รับ request": attributes + คลาส กลายเป็น Map... + route handler

สรุป

  • [Route] + [HttpGet] + คลาส → MapGroup + Map{Verb} + route handler
  • constructor ที่รับ TodoDb → parameter ที่ DI เติมให้เอง
  • Ok/NotFound/BadRequest/NoContent → TypedResults.* ตัวเดียวกันทุกสถานะ
  • CreatedAtAction → TypedResults.Created(path, ...) (201 + Location)
  • ของที่ไม่เปลี่ยน: DI, EF Core, DTO, pipeline, Kestrel — เปลี่ยนแค่เปลือกรับ request
  • จุดที่ต่างจริงๆ ตอนนี้คือ validation ไม่วิ่งเอง ถ้าไม่ AddValidation()
