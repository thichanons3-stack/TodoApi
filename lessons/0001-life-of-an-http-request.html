บทที่ 1 จาก 6 · Controller-based vs Minimal API

ชีวิตหนึ่งของ HTTP Request

ก่อนจะเลือกว่าจะใช้ Controller หรือ Minimal API เราต้องเห็นภาพให้ชัดเสียก่อนว่า request หนึ่งฉบับเดินทางเข้ามาในแอปของคุณอย่างไร สองสไตล์ต่างกันที่ "วิธีจัดการ request" ไม่ใช่ "กลไกข้างใน" และกลไกข้างในที่ว่า = ท่อ (pipeline) ที่คุณเห็นใน Program.cs นั่นเอง

เป้าหมายบทนี้

จบบทนี้ คุณจะอ่าน Program.cs ของตัวเองออกทุกบรรทัด และชี้ได้ว่า request GET /api/todoitems เดินผ่านอะไรบ้าง กว่าจะกลายเป็น JSON อย่างที่เห็นในผลลัพธ์

ผู้เล่นหลัก 5 ตัว

ใครทำอะไรอยู่ตรงไหนในโค้ดคุณ
Kestrelweb server — รับและส่ง HTTP bytesถูกเปิดใช้โดย app.Run()
DI Containerคลังของที่ลงทะเบียนไว้ พร้อม "ยัด" ให้คนที่ขอbuilder.Services.*
Middlewareด่านตรวจที่ request ต้องผ่านทีละด่านapp.UseHttpsRedirection()
Routingจับคู่ URL + method เข้ากับ endpointapp.MapControllers()
Controllerที่ทำงานจริงต่อ request หนึ่งๆControllers/*.cs

ครึ่งแรกของ Program.cs = สั่งของ  ·  ครึ่งหลัง = ต่อท่อ

นี่คือภาพใหญ่ที่ทำให้ Program.cs ทุกโปรเจกต์อ่านออกง่ายขึ้นมาก ให้จำเส้นแบ่งที่ var app = builder.Build(); 

// ===== ครึ่งที่ 1: "สั่งของ" — ลงทะเบียนบริการเข้า DI container =====
// ยังไม่มีอะไรทำงานจริงตอนนี้ มีแต่การ "ลงรายการ" ว่ามีของอะไรบ้าง
builder.Services.AddControllers();          // ของ: กลไก controller ทั้งชุด
builder.Services.AddOpenApi();              // ของ: ตัวสร้างเอกสาร OpenAPI
builder.Services.AddDbContext<TodoDb>(...); // ของ: TodoDb แบบ scoped — ใหม่ทุก request

// ===== เส้นแบ่ง: ปิดการสั่งของ =====
var app = builder.Build();

// ===== ครึ่งที่ 2: "ต่อท่อ" — ประกอบร่าง pipeline ของ request =====
app.UseHttpsRedirection();  // ด่านที่ 1: ถ้ามาทาง http ให้เปลี่ยนเส้นทาง
app.MapControllers();       // ด่านสุดท้าย: จับ URL ไปหา action ใน controller
app.Run();                  // เปิดก๊อก — Kestrel เริ่มฟัง request

ทุกครั้งที่เห็น AddSomething() ให้คิดว่า "กำลังลงทะเบียนของเข้าคลัง" และทุกครั้งที่เห็น app.Use...() หรือ app.Map...() ให้คิดว่า "กำลังต่อการ์ดเข้าท่อ" request จะไหลผ่านการ์ดตามลำดับที่เขียนนั่นแหละ [Microsoft Learn: Middleware]

เดินตาม request: GET /api/todoitems

ตอนนี้มาดู request จริงจากไฟล์ TodoApiV2.http ของคุณ เดินผ่าน 5 ด่านนี้:

① Kestrel รับ request      GET http://localhost:5018/api/todoitems
        ↓
② UseHttpsRedirection     (ด่าน middleware แรก — ข้ามไปถ้าเป็น https อยู่แล้ว)
        ↓
③ Routing จับคู่ URL       [Route("api/[controller]")] + TodoItemsController
   → เส้นทางฐาน = api/TodoItems   +   [HttpGet] ไม่มี parameter
   → ตรงกับ action: GetTodoItems()
        ↓
④ DI สร้าง controller ใหม่  new TodoItemsController(todoDb)
   (ของที่ constructor ขอด้านบน ถูกยัดใส่ให้อัตโนมัติ)
        ↓
⑤ GetTodoItems() ทำงาน     query SQLite → แปลงเป็น TodoItemDTO
   return Ok(result)       → ส่งกลับเป็น JSON + สถานะ 200

Aha! #1 — ทำไม URL ตัวเล็กตัวใหญ่ไม่สำคัญ

[Route("api/[controller]")] + ชื่อคลาส TodoItemsController ถูกแทนที่เป็น api/TodoItems โดย ASP.NET ตัดคำว่า "Controller" ท้ายชื่อออกให้ และ routing ไม่สนใจตัวพิมพ์ ดังนั้นทั้ง /api/TodoItems และ /api/todoitems จึงชี้ไป action เดียวกัน

Aha! #2 — Controller ถูก "new" ใหม่ทุก request

คุณไม่เคยเขียน new TodoItemsController(...) เองเลย ใช่ไหม? นั่นเพราะ DI container เป็นคนสร้างให้ — และ ทุก request ได้ controller คนละตัว พร้อม TodoDb (scoped) คนละ instance ด้วย นี่คือเหตุผลที่ constructor injection ปลอดภัย: แต่ละ request ไม่แย่งของกันใช้

ลองของจริง (5 นาที)

เปิด terminal ในโฟลเดอร์โปรเจกต์ แล้วทำตามลำดับ:

  1. รันแอป: dotnet run — รอข้อความว่าแอปกำลังฟังที่ localhost:5018
  2. เปิดไฟล์ TodoApiV2.http แล้วกด Send Request ที่ request แรก (GET categories) — ถ้ายังไม่มี request ของ todoitems ให้เพิ่มเอง: 
    GET http://localhost:5018/api/todoitems
Accept: application/json
  3. ตอบในใจก่อนกดส่ง: "ด่านไหนบ้างที่ request นี้ต้องผ่าน?" แล้วส่ง — ถ้าได้ 200 OK พร้อม JSON แปลว่าเดาถูก
  4. กลับมาเปิด Program.cs อ่านอีกรอบ แล้วชี้ทีละบรรทัดว่า "บรรทัดนี้ อยู่ตรงไหนใน 5 ขั้นตอนเมื่อกี้"

1 · บรรทัด app.MapControllers(); ทำหน้าที่อะไร?

MapControllers() ไม่ได้ลงทะเบียนอะไรเลย — มันไปอ่าน [Route] และ [HttpGet] ที่ติดอยู่บน controller ทุกตัว แล้วสร้างตารางเส้นทางใส่ pipeline ให้ต่างหาก ส่วนการลงทะเบียนกลไก controller ทั้งชุดเป็นหน้าที่ของ AddControllers() ในครึ่งแรกของ Program.cs

2 · เมื่อมี GET /api/todoitems เข้ามา ใครเป็นคนสร้าง TodoItemsController?

DI container เป็นคน new ให้ทุก request — คุณไม่เคยเขียน new เองเลย และแต่ละ request ได้ instance คนละตัว พร้อม TodoDb คนละ instance ด้วย จึงไม่แย่งของกันใช้

3 · บรรทัดใดใน Program.cs ลงทะเบียน TodoDb ให้ controller ยืมใช้?

AddDbContext<TodoDb>() คือบรรทัดที่ลงทะเบียน TodoDb แบบ scoped (ใหม่ทุก request) ส่วน AddOpenApi กับ AddControllers เป็นคนละของกัน และ UseHttpsRedirection อยู่ครึ่งหลังของไฟล์ คือครึ่ง "ต่อท่อ" ไม่ใช่ครึ่ง "สั่งของ"

4 · ทำไม controller ถึงมี TodoDb พร้อมใช้ใน constructor โดยคุณไม่ต้องเขียน new เอง?

ตอน DI container จะสร้าง instance มันดูก่อนว่า constructor ขออะไร แล้วยัดใส่ให้ตรงนั้นพอดี — นี่คือ constructor injection และเป็นเหตุผลของ Aha! #2 ว่าทำไมคุณไม่ต้องเขียน new เอง

5 · /api/todoitems กับ /api/TodoItems ต่างกันอย่างไร?

ชื่อ [controller] ถูกแทนด้วยชื่อคลาสที่ตัดคำว่า Controller ท้ายชื่อออก แล้ว routing ก็ไม่สนใจตัวพิมพ์ ทั้งสอง URL จึงชี้ไป action เดียวกันเป๊ะ — ผลลัพธ์ที่ได้เหมือนกันทุก byte

6 · ตอนที่ action ทำ return Ok(result); เกิดอะไรขึ้น?

Ok(result) คือส่ง object กลับเป็น JSON พร้อมสถานะ 200 — ไม่มีการเขียนลง database เพิ่ม ไม่ได้แปลงเป็น HTML และไม่ต้องสร้าง controller ใหม่ เพราะทุกอย่างเกิดขึ้นใน action เดิม

สรุป

  • Program.cs ครึ่งแรก = ลงทะเบียนของ (DI) · ครึ่งหลัง = ต่อท่อ (pipeline)
  • Routing แปลง [Route("api/[controller]")] + ชื่อคลาส เป็นเส้นทาง และจับคู่กับ method + URL
  • Controller และ TodoDb ถูกสร้างใหม่ ทุก request โดย DI — คุณไม่ต้อง new เอง
  • Ok(result) = ส่ง JSON กลับพร้อมสถานะ 200
