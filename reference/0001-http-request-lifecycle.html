วงจรชีวิต HTTP Request ใน ASP.NET Core

สรุปอัดแน่นจาก บทที่ 1 — อ้างอิงพฤติกรรมจาก Microsoft Learn: Middleware และ APIs overview (.NET 10)

1. เส้นทาง request (pipeline)

Client ──HTTP──▶ Kestrel ──▶ [Middleware ที่ 1] ──▶ [Middleware ที่ 2] ──▶ …
                                                          │
                                            Routing จับคู่ URL กับ endpoint
                                                          │
                            Controller action ถูกเรียก (instance ใหม่ต่อ request)
                                                          │
                       ผลลัพธ์ถูกแปลงเป็น JSON ──▶ ส่งกลับตามท่อเดิม (ย้อนกลับ)
  • Kestrel — web server ที่ WebApplication.CreateBuilder ตั้งค่าให้ ทำหน้าที่รับ/ส่ง bytes ของ HTTP
  • Middleware — ด่านตามลำดับที่ request ต้องผ่าน แต่ละด่านทำงานก่อนและ/หรือหลังส่งต่อ (next)
  • Routing — จับคู่ HTTP method + URL กับ endpoint ที่ลงทะเบียนไว้
  • WebApplication เพิ่ม UseRouting / UseEndpoints ให้เอง — เราไม่ได้เขียนเอง แต่มันทำงานจริง

3. การจับคู่เส้นทาง (route matching) ของแอปนี้

ในโค้ดแปลงเป็นตัวอย่าง URL ที่ใช้ได้
[Route("api/[controller]")]
+ class TodoItemsController		 api/TodoItems
(ตัดคำว่า "Controller" ท้ายชื่อคลาส)		 /api/TodoItems และ /api/todoitems — ใช้ได้ทั้งคู่ ตัวพิมพ์ไม่สำคัญ
[HttpGet] / [HttpGet("{id}")] GET / GET พร้อม parameter /api/todoitems → GetTodoItems()
/api/todoitems/3 → GetTodoItem(3)
[HttpPost] / [HttpPut("{id}")] / [HttpDelete("{id}")] POST / PUT / DELETE ตรงกันข้าม — method ต้องตรงด้วย ไม่งั้น 405

4. กฎที่ต้องจำ (ตัวย่อไว้ทบทวน)

  • DI สร้างของเมื่อ "ถูกขอ" ไม่ใช่ตอนลงทะเบียน — AddDbContext แค่สั่งจอง ของจริงถูกสร้างเมื่อมี request มาหา controller
  • Controller = new ใหม่ทุก request (ค่าเริ่มต้น) — ของที่ constructor ขอ จะถูกยัดใส่ให้อัตโนมัติ
  • Scoped = หนึ่ง instance ต่อหนึ่ง request — request คนละ request ได้ TodoDb คนละตัว ไม่ชนกัน
  • Ok(x) = ผลลัพธ์ + สถานะ 200 — จากนั้น JSON serializer แปลง object เป็น bytes ให้เอง
  • ลำดับ middleware สำคัญ — ที่เขียนใน Program.cs คือลำดับที่ถูกเรียกจริง
